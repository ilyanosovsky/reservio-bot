# CLAUDE.md — padel-bot

## Что это за проект

Автономный бот бронирования падел-кортов на Padel Port Batumi (Reservio).

**Дроп-модель (подтверждена живым наблюдением 30.07.2026, зафиксирована как
истина):** слоты открываются ПОЧАСОВО, rolling T+7. Слот на час `H` дня T+7
появляется в availability примерно в `(H-1):58:50–59:00` дня T. Наблюдение:
слот 06.08 10:00 появился 30.07 между 10:58:49 и 10:58:59, бронь confirmed
через 1.1 c. Следствие для цели 20:00+21:00: это ДВА отдельных дропа —
~19:58:50 (слот 20:00) и ~20:58:50 (слот 21:00) дня T.

Бот должен успеть забронировать **Padel Court 3** (fallback: **Padel Court 2**)
на **20:00 и 21:00** быстрее конкурентов, плюс Telegram-интерфейс для управления.
Бот мультипрофильный (см. «Мультипрофили» ниже).

**Архитектурный принцип: путь A.** Ядро — детерминированный код (cron + прямые
вызовы Reservio API v2). Никакого LLM в core-флоу. LLM появится только в фазе 2
как парсер свободных запросов из Telegram. Никаких browser-агентов.

## Ключевые факты (не переспрашивать, они проверены)

- API: `https://api.reservio.com/v2`, формат JSON:API
  (`Accept: application/vnd.api+json`), auth НЕ нужен (guest-флоу).
  Полный протокол: `docs/PROTOCOL.md`.
- businessId: `1e32bd0a-0d5c-4e30-9788-ea488e713c4d`
  (⚠️ НЕ `b442467d…` — то id картинки, см. PROTOCOL.md)
- Отмена: `PATCH /bookings/{id}?token={token}`, `state: "canceled"` (одна L!),
  успех — только по `state === "canceled"` в ответе. `token` из ответа POST
  ОБЯЗАТЕЛЬНО сохранять в state — без него бронь не прочитать и не отменить.
- Каждый корт = отдельный **service**. serviceId — в `docs/PROTOCOL.md`.
- Таймзона клуба: `Asia/Tbilisi` (**+04:00, без DST**). ВСЁ расписание — только
  в этой таймзоне, никогда в таймзоне сервера.
- Слот длится **59 минут**. «Игра 2 часа» = **два отдельных booking**
  (20:00 и 21:00).
- Бронь создаётся как guest: `name/email/phone` в payload. Email аккаунта
  владельца привязывает бронь к его личному кабинету. Логин/пароль/Google OAuth
  НЕ нужны (если spike не покажет обратное).
- Цена GEL 80 — оплата в клубе. Никаких платёжных шагов в API-флоу нет.

## Открытые вопросы (фаза 1 закрыта 30.07.2026, детали в docs/PROTOCOL.md)

1. ~~Bearer-токен~~ — НЕ нужен: весь guest-флоу (read + POST bookings +
   PATCH cancel) работает без Authorization.
2. ~~Endpoint отмены~~ — `PATCH /bookings/{id}?token={token}` со
   `state: "canceled"` (одна L!); token приходит в ответе POST /bookings
   и ОБЯЗАН сохраняться в state.
3. ~~2 брони подряд~~ — да, пускает (интервал ~3 сек, обе confirmed).
4. ~~Секунда дропа~~ — почасовая rolling-модель: слот часа H дня T+7
   появляется в ~(H-1):58:50–59:00 дня T (одно наблюдение 30.07, принято
   как истина; вечерние прогоны уточнят разброс секунд).

## Правила для агента

- **`spike-reservio.ts --book` создаёт РЕАЛЬНУЮ бронь.** Запускать только когда
  пользователь явно попросил в текущей сессии. Без `--book` скрипт безопасен.
- Никогда не хардкодить и не логировать `CLIENT_*` данные и токены — только env.
- Не превращать polling в DDoS: интервал ≥ 2 секунды, окно ≤ 5 минут,
  экспоненциальный backoff при 429/5xx.
- Успех брони = получен `booking_id` от API (внешняя валидация). Никогда не
  считать бронь успешной по отсутствию ошибки или по «кажется, сработало».
- Идемпотентность: повторный запуск джобы не должен создавать дубль брони —
  перед POST проверять state и/или список броней.
- Инвариант наблюдаемости: КАЖДЫЙ вечер в 21:0x в Telegram уходит ровно одно
  сообщение — успех / ошибка / «пропущено по команде». Молчаливый провал —
  худший баг этого проекта.
- Все даты в коде: ISO с явным оффсетом `+04:00`
  (пример: `2026-08-05T20:00:00+04:00`). Не использовать `new Date()` без
  явной работы с таймзоной.
- Пока идёт разработка (фазы 0–3) — никаких автоматических бронирований по
  cron. Cron включается только в фазе 4 после явного одобрения пользователя.

## Мультипрофили

Бот обслуживает НЕСКОЛЬКО профилей на одном клубе (пользователь + его девушка,
дальше возможно больше). Профиль = { id, контакт (name/email/phone — каждому
свой email, бронь привязывается к его кабинету), telegram chat_id, правила:
времена слотов, приоритет кортов, дни недели }. Вся логика engine/scheduler
параметризуется профилем — НИКАКИХ захардкоженных «20:00 Court 3» в коде,
только в конфиге профиля. У каждого профиля свои дропы (почасовая модель).

## Процесс разработки (требования пользователя, обязательны)

- Репо: `github.com/ilyanosovsky/reservio-bot`, ветка `main` — protected.
- ЛЮБОЕ изменение — через PR из feature-ветки. Прямых пушей в main нет.
- Каждый PR ревьюит бот **charliecreates**; его комментарии отрабатываются
  и явно резолвятся (reply + resolve), конфликты разрешаются.
- Мерджит ТОЛЬКО пользователь, и только когда всё зелёное (CI + ревью).
- Тесты: vitest, обязательны для core-логики (движок, scheduler, клиент).
- Документация: wiki/доки поддерживаются в актуальном состоянии в каждом PR.

- Сложные задачи (engine, клиент API, архитектура) — Opus.

## Стек

- TypeScript, Node 20+ (native fetch), pnpm; никаких лишних зависимостей в core
- Telegram: grammY
- State: SQLite (`better-sqlite3`) локально — таблицы bookings, settings;
  интерфейс StateStore абстрактный (в облаке trigger.dev файловой SQLite нет —
  драйвер заменится на внешнюю БД в фазе 4)
- Cron/джобы: **trigger.dev** (решено), project ref `proj_fxjnzqesxsicrpeuepzv`;
  env: `TRIGGER_SECRET_KEY_DEV` / `TRIGGER_SECRET_KEY_PROD`
- Хостинг Telegram-бота: решается в фазе 4 (кандидаты: Railway, Northflank,
  Vercel webhooks; критерий — бесплатно/дёшево, всегда доступен). Core-модули
  писать хост-агностично: чистые функции + тонкие адаптеры.

## Структура (целевая)

```
src/
  reservio/client.ts      # API-клиент (auth, availability, book, cancel, list)
  reservio/types.ts
  core/booking-engine.ts  # polling + бронь 20:00/21:00, Court 3 → Court 2
  core/scheduler.ts       # расчёт времён: дроп 21:01, напоминание T-2ч (Asia/Tbilisi)
  core/state.ts           # SQLite: брони, skip-флаги, дедупликация
  bot/                    # grammY: команды, кнопки, уведомления
  index.ts
spike-reservio.ts         # фаза 1: проверка протокола (см. PLAN.md)
docs/PROTOCOL.md          # извлечённый протокол Reservio API v2
PLAN.md                   # фазы разработки с критериями приёмки
```
