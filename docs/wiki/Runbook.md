# Runbook

Статус на ветке `feat/booking-engine` (фаза 2): весь `src/*` (клиент,
scheduler, state, профили, `booking-engine.bookSlotDrop`, `run-drop.ts`,
`trigger/book-drop.ts`) реализован и покрыт тестами (vitest). Telegram-бот
(`bot/`) — фаза 3, ещё не начат: до тех пор результат прогона нужно смотреть
в консоли/логах trigger.dev вручную.

Перед любым запуском: `cp .env.example .env` и заполнить `CLIENT_NAME`,
`CLIENT_EMAIL`, `CLIENT_PHONE` (email — от Reservio-аккаунта владельца, бронь
привяжется к его личному кабинету). Для второго профиля — переменные
`PROFILE_<K>_NAME/EMAIL/PHONE/TIMES/COURTS` (пример — комментарий в
`src/core/profiles.ts`).

## `run-drop.ts` — ручной прогон дропа (dry-run / `--live`)

```bash
npx tsx src/run-drop.ts --profile ilya --date 2026-08-06 --time 20:00                 # dry-run: безопасно
npx tsx src/run-drop.ts --profile ilya --date 2026-08-06 --time 20:00 --live          # РЕАЛЬНАЯ бронь
npx tsx src/run-drop.ts --profile ilya --date 2026-08-06 --time 20:00 --court "Padel Court 2"
```

Флаги: `--profile` (id профиля, по умолчанию `ilya`), `--date` YYYY-MM-DD,
`--time` HH:MM — оба обязательны, `--live` — включает реальный `POST`,
`--court` — переопределяет приоритет кортов профиля одним конкретным кортом,
`--force` — снимает проверку `daysOfWeek` из правила профиля (без него запуск
в «не свой» день недели прекращается с кодом 2 и ничего не бронирует).

- **Без `--live` (dry-run, по умолчанию)** — движок работает по-настоящему:
  ждёт начало окна наблюдения, поллит availability, при появлении слота
  проверяет идемпотентность, но вместо реального
  `createBooking` пишет в лог `[DRY] бронировал бы: serviceId=... start → end`
  и возвращает синтетический `BookingCreated` (`bookingId: dry-<timestamp>`,
  `token: 'dry-token'`). Безопасно гонять для проверки таймингов и
  fallback-логики. **State у dry-run отдельный — `state.dry.db`**: фиктивная
  бронь в боевом `state.db` заблокировала бы последующий `--live` прогон того
  же слота (`AlreadyBooked`, ни одного `POST`).
- **С `--live`** — тот же движок, но `createBooking` реальный: настоящий
  `POST /bookings`, реальная бронь. Использовать только по явной просьбе
  пользователя в текущей сессии.

Если запущен раньше окна наблюдения — скрипт сам ждёт его начала и раз в 30 c
логирует, сколько секунд осталось (`окно наблюдения ещё не началось, старт
через ~Nс`); все метки времени — в зоне клуба (+04:00), как и у движка. Если
окно уже закрылось или откроется позже чем через сутки (промах в `--date`),
скрипт выходит с кодом 2 и подсказкой проверить `--date/--time`.
В конце — блок `--- Результат ---` (✅/✗) и `DropReport` в виде JSON;
`token` в выводе заменён на `<сохранён в state.db>` (полностью печатается
только если сохранить его в state НЕ удалось — тогда это единственный след
брони).

## Что смотреть в логах

Каждая строка от `ReservioClient`/движка начинается с ISO-таймстемпа. Обращать
внимание на:

- **`availability`**: HTTP-статус и число слотов на каждый polling-запрос;
  появление целевого `start` в списке — это и есть зафиксированный дроп,
  сравнивать момент с моделью `H:58:50–59:00` дня T
  (см. `Architecture.md` → «Дроп-модель») и при заметном расхождении
  фиксировать в `docs/PROTOCOL.md`.
- **Backoff, два уровня**: (1) внутри одного HTTP-запроса `ReservioClient`
  ретраит `GET`/`PATCH` до 3 раз на `429`/`5xx` (строка `повтор через Nms
  (попытка X/3)`, 1 c→2 c→4 c, потолок 30 c, уважает `Retry-After`);
  (2) между раундами polling `booking-engine` держит свой backoff 2 c→4 c→8 c
  →16 c→30 c, если целый раунд опроса упал с ошибкой. На `createBooking`
  (POST) ретраев нет вообще на обоих уровнях: каждый корт получает **ровно
  одну** попытку `POST` за запуск, и когда попытки исчерпаны, движок
  прекращает polling досрочно.
- **Неоднозначный отказ `POST`** (таймаут 5 c, обрыв связи, `5xx`, `2xx` без
  `data.id`) — бронь МОГЛА быть создана на сервере, поэтому движок НЕ идёт на
  следующий корт, а завершает дроп с `Timeout`/`ApiChanged` и текстом «бронь
  могла быть создана». Проверить почту профиля и клуб вручную: у такой брони
  нет ни `bookingId`, ни `token`, отменить её через API нельзя.
  На детерминированный отказ (`4xx`, например `409` — слот перехватили)
  движок сразу переходит к следующему корту по приоритету профиля.
- **`AlreadyBooked`**: если в `state.db` уже есть непогашенная запись на этот
  `(profileId, date, time)`, движок не делает `POST` вовсе — это ожидаемая
  идемпотентность, не баг, но при неожиданном появлении стоит проверить,
  откуда взялась запись (дубль запуска, старый прогон).
- **`createBooking: id=... state=...`** — единственное подтверждение успешной
  брони. Если в логе видно `ВНИМАНИЕ — в ответе нет token` — это критично,
  без токена бронь нельзя ни прочитать, ни отменить, разбираться немедленно.
- **`cancelBooking: ... → canceled`** — успех отмены. Если вместо этого
  выброшена ошибка `бронь не отменена, state="..."` — API вернул 200-эхо
  без реальной отмены (см. «Как отменить бронь» ниже).
- Итоговый `DropReport` (`ok`/`error.kind`) в конце `run-drop.ts` — по нему
  видно, был ли fallback на второй корт и какая именно ошибка, если бронь не
  удалась.

## Как отменить бронь

Отдельной CLI-команды отмены в `run-drop.ts` пока нет — использовать
спайк-скрипт фазы 1:

```bash
npx tsx spike-reservio.ts --cancel <bookingId> --token <token>
```

Под капотом то же, что делает `ReservioClient.cancelBooking`:
`PATCH /businesses/{businessId}/bookings/{bookingId}?token={token}` с телом
`{"data":{"type":"booking","id":"{bookingId}","attributes":{"state":"canceled"}}}`.

Важно (см. `docs/PROTOCOL.md`):
- Ровно `"canceled"` (одна L). `"cancelled"` API молча игнорирует и отдаёт
  200-эхо со старым `state` — успех отмены проверять по
  `data.attributes.state` в ответе, а не по HTTP-коду.
- Дедлайн отмены — за 1 час до начала слота.
- `bookingId` и `token` — из вывода `run-drop.ts --live` (поле в
  `DropReport`) или напрямую из `state.db` (см. ниже); списка всех броней
  гостю API не отдаёт (`GET /bookings` → 403).

## Где лежит state

`src/run-drop.ts` открывает `SqliteStateStore('./state.db')` для `--live`
и `./state.dry.db` для dry-run — файлы в корне репозитория (WAL-режим,
`better-sqlite3`). Таблица
`bookings`: `profileId, date, time, court, bookingId, token, state, createdAt`,
`PRIMARY KEY (profileId, date, time)` — это и есть дедупликация: на один
слот одного профиля может существовать максимум одна активная запись.
Файл в `.gitignore` (`*.db`), в репозиторий не коммитится.

В облаке (`src/trigger/book-drop.ts`, запуск через trigger.dev) файловая ФС
недоступна воркерам — там используется `MemoryStateStore`: состояние живёт
только в рамках одного run и не переживает рестарт или следующий запуск
(идемпотентность между отдельными запусками таска пока не гарантирована —
TODO фазы 4, внешняя БД). Для локальных прогонов `run-drop.ts` идемпотентность
полноценная — повторный запуск на ту же дату/время/профиль не создаст дубль.

## Ручной запуск через trigger.dev (без cron)

Таск `book-slot-drop` (`src/trigger/book-drop.ts`, project
`proj_fxjnzqesxsicrpeuepzv`) запускается **только вручную** — через дашборд,
`trigger.dev` CLI или `mcp__trigger__trigger_task` с payload
`{profileId, date, time, live, force?}`. Таск ограничен
`concurrencyLimit: 1` (два параллельных run'а не столкнутся) и не ретраится
автоматически; `token` в логи и в output рана НЕ выводится (управлять бронью
можно по ссылке из письма-подтверждения). Повторный ручной запуск с
`live: true` на уже забронированный слот всё ещё создаст дубль — общего
хранилища между run'ами пока нет (TODO фазы 4).
В конфиге (`trigger.config.ts`) нет
`schedules` — это осознанное ограничение: автоматические бронирования по
cron включаются только в фазе 4 после явного одобрения пользователя
(см. `CLAUDE.md`).

## Чек-лист вечернего боевого прогона

1. За 10–15 минут до дропа: `.env` заполнен и актуален (`CLIENT_*`/профили).
2. Проверить `docs/PROTOCOL.md`/`PLAN.md` на открытые блокеры для сегодняшнего
   запуска.
3. Запустить `npx tsx src/run-drop.ts --profile ilya --date <T+7> --time 20:00 --live`
   заранее (не более чем за сутки) — скрипт сам дождётся окна наблюдения
   `H:58:30` дня T.
4. Следить за логом до появления целевого слота и результата `POST`.
5. После брони — сверить `bookingId`/`token` в `DropReport`, дождаться письма
   на `CLIENT_EMAIL`.
6. Пока Telegram-бота нет (фазы 0–2) — результат (успех/частичный/ошибка)
   фиксировать вручную; автоуведомления появятся в фазе 3.
7. Для пары 20:00+21:00 — повторить шаги 3–5 отдельным запуском
   `--time 21:00` (это второй, независимый дроп, ~21:58:50 дня T).
8. Если что-то пошло не по модели (слот появился не в ожидаемое окно, иное
   поведение API) — зафиксировать факт в `docs/PROTOCOL.md`, не полагаться
   на память.
